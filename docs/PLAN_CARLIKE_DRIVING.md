# 계획: 자동차처럼 주행하기 (뒤축 회전, Reeds-Shepp)

작성 2026-11-26. 1~5단계 구현 2026-11-27 (각 단계의 결과는 단계 끝에 적음). 아래 수치·설정 중 "확인 필요"로 적은 것은 시험하지 않았다.

## 요구 조건

- 로봇은 제자리에서 돌 수 없다. 서 있으면 회전 0, 달릴 때도 `|w| ≤ |v| / R` (R = 최소 회전 반경).
- 방향 전환은 전·후진하며 좌우 선회(3점 회전)로만 한다.
- 회전 중심은 **뒷바퀴 축** (앞바퀴 조향차와 같은 궤적).
- 평소에는 인도(보행로·횡단보도, 없으면 차도 바깥 길가)로 다니고, 차도는 목표가 차도에 있을 때만 그 근처에서 나간다 (2026-11-27 구현, `surface.py`).

## 결정

- 실물은 앞바퀴 조향식이지만, 조향 관절을 넣는 모델 교체는 하지 않는다. 모델 구조·외형은 그대로 둔다.
- 뒤축 회전은 **바퀴 옆마찰을 앞뒤로 다르게** 줘서 만든다 (뒷바퀴는 옆으로 안 미끄러지고, 앞바퀴는 미끄러짐). 확인 필요.
- 자체 계획기(`kinematic_planner.py`)·추종기를 Reeds-Shepp 방식으로 고친다. 더 나은 오픈소스가 있으면 가져온다 (3단계 준비에서 결정).
- 최소 회전 반경 R = 1.8 m 로 시작 (축거 1.24 m, 조향각 35° 가정). 실물 값을 알면 바꾼다.

## 지금 상태

- 4륜 구동 스키드 스티어 (`DiffDrive`, 조향 관절 없음). 회전 중심은 차체 가운데, 제자리 회전 가능.
- 바퀴 마찰 방향(`fdir1`)을 넣어 회전이 명령의 94~99% (빈 Gazebo, 2026-11-26).
- 경로 계획은 Dubins + 후진 원호를 섞은 자체 Hybrid A*. Reeds-Shepp 아님.

## 단계

순서대로 진행하고, 각 단계의 완료 기준을 통과해야 다음으로 간다.

### 1단계. 뒤축 회전 만들기 (모델)

- `build_blender_models.py` 와 `model.sdf` 에서 앞·뒤 바퀴 마찰을 나눈다. 뒤: 옆마찰 크게. 앞: 옆마찰 0 근처.
- 빈 Gazebo(별도 `GZ_PARTITION`)에서 잰다: 회전 중심 위치, 명령 대비 실제 회전, 1.2 m/s 선회 때 뒤 밀림.
- 앞바퀴 옆마찰 값은 재면서 정한다.
- 완료 기준: 회전 중심이 뒤축에서 ±0.15 m, 회전 정확도 90% 이상.
- 안 되면: 차체 가운데 회전을 유지하고 2단계로 간다 (기준점 `base_footprint`).

**결과 (2026-11-27, 통과):** 앞바퀴 옆마찰 0.1, 뒤 1.0 (`build_blender_models.py` 의 `FRONT_SIDE_MU`, `REAR_SIDE_MU`).

| 명령 | 이전 (앞뒤 0.6) 회전 중심 | 지금 회전 중심 | 지금 회전 정확도 |
|---|---|---|---|
| 제자리 0.5 rad/s | +0.20 m | -0.62 m | 99% |
| R 1.8 m, 0.5 / 1.2 m/s 전진 | +0.62 m (앞축) | -0.62 / -0.61 m | 100% |
| R 1.8 m 후진 0.5 m/s | -0.62 m | -0.62 m | 99% |

- 1.2 m/s 선회 때 뒤축 옆속도 0.004 m/s (뒤 밀림 없음). 옆경사 10% 에서도 같은 값.
- 평지·옆경사의 빈 world 측정이다. 경사 지형 캠퍼스 전체에서는 재지 않았다.
- 마찰 변경 뒤 Gazebo k04·k06·k07·k08 통과 (수거 오차 5 cm·4° 이내). 도킹은 snap 방식이라 도킹 정확도는 확인되지 않는다.
- 이전 상태는 전진 때 앞축, 후진 때 뒤축으로 돌았다 (차체 가운데 회전이 아니었음).

### 2단계. 기준 좌표계를 뒤축으로

- 고정 TF `base_footprint → rear_axle` (x = -0.62 m). 계획·추종은 `rear_axle` 기준으로 한다.
- 차체 윤곽을 뒤축 기준으로: x -0.36 ~ 1.58 m, 반폭 0.525 m (+여유). 지금은 `base_footprint` 기준 -0.98 ~ 0.96.
- 다른 노드(수거·도킹·로봇팔)가 쓰는 pose 는 `base_footprint` 그대로 두고, 주행 목표만 변환한다.
- `fake_base`(kinematic)도 뒤축 회전으로 움직이게 한다.
- `DiffDrive` 오도메트리는 가운데 회전을 가정하므로 어긋난다. `sim_localizer` 가 보정하는지 확인.
- 완료 기준: 변환 단위 테스트, kinematic 과 Gazebo 의 회전 중심 일치.

**결과 (2026-11-27):** `motion.py` 에 `to_rear` / `from_rear`, 뒤축 기준 윤곽 `REAR_BODY_X` = -0.36 ~ 1.58 m. 계획·추종·후진 도킹만 뒤축 기준이고 `GoToPose` 와 다른 노드의 pose 는 그대로. 정적 TF `rear_axle` 추가, `fake_base` 도 뒤축 회전. `sim_localizer` 는 DiffDrive 오도메트리가 선회 중 옆으로 어긋나므로 보정 계수를 0.1 -> 0.6 으로 올림.

### 3단계 준비. 주행 오픈소스 조사

3단계를 시작하기 전에 가져다 쓸 만한 것이 있는지 조사한다. 자체 코드를 고치는 것보다 확실히 나을 때만 바꾼다.

- 볼 후보 (이름만 적은 것. 지원 환경·기능은 모두 확인 필요):
  - 주행 전체: Autoware (freespace planner), CMU autonomy stack, Move Base Flex
  - 계획기·추종기만: OMPL (Reeds-Shepp), TEB local planner. 라이브러리로 붙일 수 있는지 본다.
  - 조사하면서 새로 찾은 것도 후보에 넣는다.
- 비교 기준:
  - ROS 2 Humble, arm64 에서 설치·빌드되는가
  - 제자리 회전 없이 후진을 포함한 경로를 계획하고 따라가는가 (R = 1.8 m)
  - 캠퍼스 크기 야외 지도, 노면별 비용(인도 우선)을 지원하는가
  - 이 VM 의 CPU 로 돌아가는가
  - 라이선스, 최근 유지보수, 지금의 `GoToPose` 인터페이스에 붙이는 작업량
- 결과물: 자체 코드 수정안을 포함한 비교표와 추천 1개. 어느 것으로 갈지 정한 뒤에 3단계를 시작한다.
- 다른 것을 고르면 3단계와 4단계를 그에 맞게 고친다.

**결과와 결정 (2026-11-27):** 자체 Reeds-Shepp (`reeds_shepp.py`) 를 쓴다.

| 후보 | 이 VM 에서 확인한 것 | 판단 |
|---|---|---|
| 자체 코드 + Reeds-Shepp | 추가 설치 없음. 지금의 노면 비용·`GoToPose` 그대로 | **채택** |
| OMPL | `ros-humble-ompl` 1.7.0 설치돼 있음, Python 바인딩 없음 | C++ 노드가 따로 필요 |
| Nav2 Smac Hybrid-A* | `ros-humble-nav2-smac-planner` 1.1.20 설치돼 있음 | 앞서 Nav2 전환을 빼기로 함. 노면 비용·수거 접근을 다시 붙여야 함 |
| TEB, Move Base Flex | `apt-cache` 로 `ros-humble-teb-local-planner`, `ros-humble-mbf-costmap-nav` 를 찾지 못함 | 소스 빌드 필요 |
| Autoware, CMU stack | 확인하지 않음 | 규모가 이 과제에 맞지 않다고 판단 |

### 3단계. 계획기·추종기를 Reeds-Shepp 로

- 계획: `kinematic_planner.py` 의 Dubins + 후진 원호를 Reeds-Shepp 로 바꾼다 (R = 1.8 m). 제자리 회전(`pivot_at_ends`)은 없앤다.
- 경로 선택: 처음 찾은 경로를 바로 쓰지 않고, 길이·후진·방향 전환 벌점이 가장 낮은 것을 고른다 (지금은 큰 고리가 생긴다).
- 추종: `PathTracker` 가 후진 구간과 전환점에서 멈췄다 가도록 고친다.
- 속도 제약: 수거·도킹 명령까지 막도록 `/cmd_vel` 한 곳에서 `|w| ≤ |v|/R` 로 자른다. 4단계와 함께 켠다.
- 인도 우선: 지금의 `GridRouter` 경유점과 노면 비용(`surface.py`)을 그대로 쓴다. 곡선 계획의 노면 배수 상한(`SURFACE_CAP`)도 유지한다.
- `GoToPose` 인터페이스는 유지한다. `standoff` 자리 찾기도 그대로 쓴다.
- 완료 기준: "1.6 m 앞, 방향 163° 반대" 목표를 제자리 회전 없이 도착. k08 먼 이동이 인도를 따라 완료.

**결과 (2026-11-27):** R = 1.8 m (계획 반경 1.98 m). 도착 연결을 Reeds-Shepp 후보 중 비용(길이, 후진 1.8배, 전환 2 m)이 가장 낮은 것으로. 격자 A* + 제자리 회전 예비 방식은 없앰: 대신 standoff 목표는 도착 방향을 풀고, 그래도 안 되면 0.8 m 직진·후진 뒤 다시 계획. 벽에 붙어 출발할 때만 2 m 안에서 차체 반폭 기준으로 빠져나온다. 캠퍼스 지도 오프라인 계산에서 도크 -> 구역 36곳 모두 계획 성공 (최대 2.5 s).

### 4단계. 제자리 회전 사용처 바꾸기

| 위치 | 지금 | 바꿀 방식 |
|---|---|---|
| `nav_bridge.py` 의 `GoToController`, 후진 대피 | 회전 후 직진 | 3단계의 계획·추종을 사용 |
| `kinematic_planner.py` | 제자리 회전 포함 | 3단계에서 제자리 회전을 없앰 |
| `collector.py` `spin_search`, `wide_search` | 돌면서 태그 찾기 | 접근이 킥보드를 정면에 두고 끝나게 하고, 못 찾으면 원호로 둘러보며 탐색. 먼저 태그 검출기 시야각 확인 |
| `collector.py` `turn_to`, `fine_align` | 회전-직진-회전 | 제거. 어긋나면 앞으로 뺐다가 다시 후진 |
| `collector.py` 후진 도킹 (`dock_step`) | 낮은 속도에서도 크게 꺾음, 시작 전 제자리 회전 | 뒤축 기준 직선 추종 + `|w| ≤ |v|/R`. 대기점 거리 1.5 → 3~4 m. 적재 자리 거리 2.07 m(가운데 기준) = 1.45 m(뒤축 기준) |
| `arm_loader.py` 뒤 하차 (2026-11-27 추가) | 로봇이 칸 앞 2.07 m 에 `GoToController`·계획 경로로 도착 | 뒤 하차 자리도 후진 적재와 같은 직선 후진으로 들어가기 |
| `dock_controller.py` (충전소) | `GoToController` | 같은 직선 후진/전진 제어 |
| `mission_manager` 출발 후진 | 직선 후진 | 변경 없음 (확인만) |
| `extended_collector.py` | 별도 회전 탐색 | extended 프로필 사용 여부 먼저 확인 |

- 완료 기준: 실행 기록에 `v ≈ 0` 이면서 `|w| > 0` 인 명령이 없음.

**결과 (2026-11-27):** 속도 제약은 `motion.car_limit` 하나를 주행·수거·도킹·도크 후진이 모두 거친다. `fake_base`·`sim_localizer` 는 "서서 도는 명령"이 오면 경고한다.
- 태그 탐색: 도착 방향 ±40°, ±75° 를 전·후진 원호(3점 회전)로 훑는다. 예전 360° 회전보다 보는 범위가 좁다 (정면 ±106°).
- 적재 자리: 대기점 3.5 / 3.0 / 2.5 / 2.0 m 에서 직선 후진. 어긋나면 3 m 앞으로 뺐다가 다시.
- 도킹(snap·precise): 도킹 직선 추종.
- extended 프로필은 수거·주행 클래스가 따로라 바꾸지 않았다 (여전히 제자리 회전).

### 5단계. 지도·시나리오 맞추기와 검증

- 폭 3 m 보행로에서는 R = 1.8 m 로 유턴할 수 없다. 3점 회전이 안 되는 곳을 점검한다.
- `build_knu_scenarios.py` 의 `loadable` 검사에 "대기점까지 Reeds-Shepp 경로가 있는가"를 추가하고 시나리오를 다시 만든다.
- 대기열 주행 거리는 방향을 고려하지 않는다. 문제가 되면 보정한다.
- 검증: 단위 테스트 → 빈 Gazebo → Gazebo k08 수거 5건 → 다른 시나리오 몇 개 → 전체 지도. kinematic 결과만으로 성공이라 판단하지 않는다.

## 위험

- 제자리 회전이 없으면 좁은 곳에서 설 자리가 줄어 수거 실패가 늘 수 있다.
- 무게중심이 차체 가운데라, 앞바퀴 옆마찰이 낮으면 빠른 선회에서 뒤가 밀릴 수 있다.
- 앞바퀴는 외형상 꺾이지 않고 옆으로 끌리듯 보일 수 있다.
- Reeds-Shepp 탐색이 이 VM 에서 충분히 빠른지 모른다.
- 후진 도킹은 자체 코드를 쓴다.
- 주행은 C 담당, 수거·도킹은 해당 담당 영역이다. `GoToPose` 인터페이스는 바꾸지 않는다.

**결과 (2026-11-27):** `build_knu_scenarios.py` 의 `loadable` 에 직선 후진 띠와 대기점까지의 Reeds-Shepp 경로 검사를 추가하고 다시 만듦 (219대 중 위치 1대, 방향 9대 바뀜, 검사 문제 0건).

**Gazebo 검증 (2026-11-27):** k04·k06·k07·k08·k19 통과, 서서 도는 명령 0건, 후진 도킹은 첫 시도에 2 cm 안.
- k04 에서 뒤 하차 직후 옆 칸으로 가다 10분 멈춤 -> 후진 안전 정지(뒤 0.25 m)와 걸림 감시(8초)를 `nav_bridge` 에 추가. 다시 돌려 같은 이동이 29초에 끝남.
- 남은 것: k19 에서 `mission_manager` 의 수거·도킹 제한 시간 초과 경고 각 1건 (자동차식 주행이 느려진 영향으로 추정, 확인 안 함). 나머지 시나리오와 캠퍼스 전체 world 는 돌리지 않음.
- 시뮬 라이다(`sim_lidar`)는 차체에 가리지 않아 뒤를 본다. 실물에는 뒤 라이다 등이 필요하다.
- 뒤 하차 직후: `/scooter_dropped` 가 로봇 뒤를 가리키면 `nav_bridge` 가 처음 1.5 m 는 전진만 하는 경로를 후보로 계획 (`plan_path(forward_first=...)`). 앞이 막혀 그런 경로가 없으면 제한 없이 다시 계획. 단위 테스트만 확인, Gazebo 는 아직.
